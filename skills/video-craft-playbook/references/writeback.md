# 回写协议：值得沉淀的才写回来

本手册不是静态文档，但也不是流水账。每做完一个视频案例（交付或中止），先判断这次有没有值得沉淀的知识：有就写回来，没有就跳过。机制分三层：

1. **收尾判断**：SKILL.md 第 4 步要求按下面第一节过一遍候选，再决定回写或跳过；最终交付说明写一行“Playbook 回写”，给出结论。
2. **欠账可见**：判断值得写、但没来得及蒸馏的案例卡留在 `cases/inbox/`。下一次使用本手册时，开工第一步 `playbook.py status` 会列出它们，提醒先还账。
3. **机器校验**：`playbook.py check` 校验能力卡字段完整与定长、总览表覆盖、验证日期存在、相对链接可达、没有孤儿文件、craft-lessons 引用 ID 存在、经验条目标签在词表内、容量上限（含通用条目上限与坑的分组上限）、没有带倾向性的措辞；`close` 只在校验通过、案例卡写明蒸馏去向后才归档，并按 slug 统计每案配额。

## 一、沉淀判断

### 1. 列候选

回看这次的过程，把可能值得写的东西列出来，每条附上证据（命令输出、对比渲染、实测数字、用户反馈）：

| 候选类型 | 例子 |
|---|---|
| 新能力 | 手册里没有的工具、模型、库、数据源 |
| 能力卡修正 | 某能力的适用、边界、代价、确定性与卡片不符；验证状态升级（推断 → 案例验证） |
| 方法、技巧 | 换个题材也能用的做法、算法、管线、审片或验收手段 |
| 通用知识 | 影响选型的事实，例如某类素材的真实约束、某个格式的兼容性 |
| 坑 | 找到根因、换个案例还可能再遇到的问题 |
| 组合 | 和已有案例明显不同的能力组合，或已有组合在新约束下的不同表现 |
| 选型提问 | 规划时漏问、事后才发现该问的问题 |

### 2. 逐条过三道门

每条候选都要过三道门，全过、且有证据的才算数：

1. **复用门**：下一个不同题材的案例，会因为它做出不同选择，或少走一段弯路吗？满足其一：会改变某个元素的能力选择、组合或接口设计；推翻或修正了手册里的现有说法；把一项能力从“推断 / 已安装未验证”升级到“案例验证”，或给出了第一份代价实测。
2. **不可推导门**：从手册已有条目加上该工具的官方文档推不出来。API 清单、参数名、版本行为这类文档能查到的内容不写，必要时留一句指针；已有条目能覆盖、这次只是又验证了一遍的不写（能力卡的“验证”日期超过复核期时，只更新那一行）。
3. **代价门（只对坑）**：静默失效（静帧、联系表、局部检查看不出，成片或下游才暴露），或根因已知、排查花了 30 分钟以上、换个案例还可能再遇。报错即知的命令行、语法、字体路径这类坑一律只记在工作区 `effects/pitfalls.md`。

任一命中即不写：
- 只对这条片子成立的细节：具体文案、配色值、某首歌的母题、参数取值。它们属于项目 README 或工作区。
- 没有证据的猜测，或没找到根因、也不知道怎么规避的偶发故障。
- 代码级实现细节：放工作区 `effects/snippets/` 或项目目录，手册最多留一句结论和指针。

### 3. 合并优先

算数的条目先找落点：在目标文件里找最近的已有条目，能加一句的就加一句，不新增；被新证据推翻的旧说法改掉。只有没有可并入的条目时才新增。案例卡“蒸馏去向”按条写明“合并进 X”或“新增（无可合并条目：原因）”。

### 4. 配额、上限与分层

- **每案配额**（`close` 按 slug 统计，超出 warn，理由写进案例卡）：craft-lessons 新增 ≤ 2 条、pitfalls ≤ 3 条、composition-patterns 1 条且 ≤ 12 行；新建能力卡 ≤ 1 张，只为手册里没有的能力建卡。
- **容量上限**（`check` 校验，超限 FAIL，`close` 拒绝归档）：craft-lessons ≤ 60 条，其中通用条目 ≤ 25 条；pitfalls 按工具分组设上限，写在分组标题里（`〔工具标签｜上限 N〕`，见“差异化分配”）；每个组合案例 ≤ 12 行、能力卡单字段 ≤ 600 字符（超 400 warn）；经验与坑单条超 300 字符 warn（不计标签），把“追加式合并”显形。常驻层满（经验到 60 条，或坑的某组到上限）时，新条目写进候补层 [lessons-backlog.md](lessons-backlog.md)（2026-10-30 经用户确认新建），不挤占、不丢。
- **标签**（2026-11-08 经用户确认）：每条经验（含候补）在标题后带一个标签，`〔通用｜阶段〕` 或 `〔条件：标签｜阶段〕`。通用指任何 vibe motion 都适用；条件标签写它在什么体裁、工具或素材下才适用。阶段取规划、执行、审片、交付，写它该在哪一步被照做，不是它从哪一步学来。词表用 `playbook.py brief --list-tags` 查，加词改脚本里的 `TAG_VOCAB`。`brief --phase <阶段> --tags <标签>` 按标签取出该检查点的通用、条件与候补条目，执行阶段附上对应工具的坑；单个检查点超过 15 条时提示标签给宽了或该合并。
- **差异化分配**（2026-11-08）：选型层等长，执行层按风险。能力卡字段定长，守中立原则；坑、技法与细则的篇幅按工具每用一次的风险分配：静默失效密度、出错代价、能力表面积、版本漂移，不按使用频次（用得多 → 写得多 → 更常被选）。坑的分组上限分四档：Remotion / 浏览器渲染、生成视频 / 图像、TTS / 音乐 / 混音 15，生成 3D 与 Blender 12，three.js、轴测与参考复刻 8，物理模拟、ffmpeg 与脚本 5；每次归纳复核档位。
- **准入**：新条目过了三道门，有本机证据的进常驻层（标条件或通用），只有外部证据的进候补。要标通用，须胜过通用条目里最弱的一条（证据来源数、防住过的缺陷、适用面），否则标条件；通用满 25 条时一进一出，案例卡“蒸馏去向”写明挤出了谁或为什么没挤。
- **计数**：案例卡“用到的手册条目”分四栏：起作用、适用但漏用、照做但误导、不适用（只记通用条目），由 `consolidate` 汇总。适用但漏用的不降级，改它的阶段标签或挂到对应检查点；照做但误导的、被新证据推翻的列为降级候选；通用条目在最近 10 个案例里记“不适用” ≥ 5 次的，改标条件。引用次数为零不是删除信号：地基条目常因已内化而少被写，题材没覆盖到的条件条目也不会被引用。
- **晋升与归纳**：候补条目满足任一才升入常驻层：第二个不同题材的案例在“起作用”栏记了它；没参与制作的审片者回溯判定后来某个缺陷本可被它防住（案例卡写明依据）；用户反馈与它一致；或它推翻了常驻层的现有说法。升入满员的层时一进一出；只有一个来源的留在候补。候补条目和常驻条目一起被 `brief` 取出并标“候补”，第二个案例才看得到它。`status` 在候补 ≥ 15 条、最老一条超过 60 天、或上次归纳以来关闭 ≥ 5 个案例时提示（上次归纳日期写在候补层开头），`consolidate` 只读地列出可晋升候选、计数、各组容量与超长条目。归纳清单按顺序：删被推翻的（有价值的历史结论注明日期保留）→ 合并同主题 → 超过 300 字的常驻条目拆成一句结论加候补细节或工作区指针 → 晋升与降级 → 组内通用条目在前、再按起作用次数排 → `check` → 更新候补层的“上次归纳”日期。外部蒸馏（只有外部证据）的条目从候补起步，本机验证后再升。
- **结构变更需用户确认**：新建 references 文件、新章节、新分组不在本协议授权内；`check` 对没有被任何文件链接的 references 文件报 FAIL。
- **分层**：capability-atlas、composition-patterns、craft-lessons、pitfalls 是经验层，每条带来源案例；editing-grammar、edit-signals 是教材层，允许推断，回写只在条目末尾标“验证 / 推翻（案例，日期）”，不按案例追加条目。
- **版本退化**：pitfalls 分组标题带工具版本，版本换了整组复核，过期条目删除或标注日期。

### 5. 定结论

- **有一条以上算数** → 走第二节回写，只写算数的那几条。
- **一条都不算数** → 跳过：不建案例卡、不登记台账、不改手册文件。交付说明写“Playbook 回写：跳过：<一句话理由>”，例如“跳过：同 city-love 组合，未出现新能力或新坑”。
- **用户说不回写** → 跳过，理由写“用户限定不回写”。
- **拿不准** → 按“不算数”处理，把这条写进交付说明，由用户决定要不要补。

“时间不够”不是跳过的理由：值得写但来不及时，建卡留在 inbox。

## 二、回写步骤

### 1. 生成案例卡

```bash
python3 ~/.agents/skills/video-craft-playbook/scripts/playbook.py new-case <slug> --title "<一句话任务>"
```

在 `cases/inbox/<日期>-<slug>.md` 生成卡片，并在 `cases/LEDGER.md` 登记一行“inbox”。按模板填写：任务与约束、实际能力分工（含比较过的替代）、用到的手册条目（按起作用、适用但漏用、照做但误导、不适用四栏填 L 号，EG 号、卡号也可写）、效果与证据、新能力或能力卡修正、新方法、新坑、代价、未验证项。没有内容的小节写“无”。只写有证据的内容，推断要标“推断”。

### 2. 蒸馏进手册

只蒸馏第一节判为算数的条目，先合并后新增。逐项判断它该去哪里，写进对应文件并标注来源案例与日期：

| 新知识 | 去向 |
|---|---|
| 常驻层已满（craft-lessons 60 条，或 pitfalls 对应工具分组到上限） | `lessons-backlog.md` 对应分节；L 号取全局最大号 +1 |
| 用到了手册里没有的工具或能力 | `capability-atlas.md` 新增一张卡（八个字段齐全） |
| 新的素材来源，某个素材库的许可或配额变化，本地索引方法有了实测 | `capability-atlas.md` H 组对应卡 |
| 某个能力的适用、边界、代价、验证状态与卡片描述不符 | 修正那张卡，更新“验证”行的案例和日期 |
| 新的组合方式、或某种组合在新约束下的表现 | `composition-patterns.md` 追加一条案例 |
| 换工具也成立的做法 | `craft-lessons.md` 对应分组追加 |
| 某个工具的坑 | `pitfalls.md` 对应工具分组追加 |
| 选型时没想到、事后发现该问的问题 | `task-lenses.md` 第一节或第五节；剪辑类任务的提问进第六节 |
| 剪辑后处理手法、“信号 → 手法”规则或参数被验证、修正或推翻 | `editing-grammar.md` 对应编号条目：标来源案例与日期，推翻的直接改 |
| 理解层信号的字段、提取方式或可靠性边界有了实测 | `edit-signals.md` 第二节对应行 |

写法要求：
- 已有条目能覆盖的就合并修正，不重复追加；被新证据推翻的旧说法改掉，有价值的历史结论注明日期保留。craft-lessons 新条目取当前最大 L 号 +1，不重排旧号。
- 经验条目标题后写〔适用面｜阶段〕标签（第一节第 4 条）；新坑写进对应工具分组，没有对应分组时属于结构变更，先问用户。
- 写成条件句：“在什么约束下、因为什么，它成立 / 失效”。不要把一次成功写成“这类片子用它”。
- 代码级细节、长排查过程放在案例所在工作区（例如 `$MG_WORKSPACE/effects/`），手册里留一句结论和指针。
- secret、token、账号信息、私人素材内容不写进手册。

### 3. 校验并归档

```bash
python3 ~/.agents/skills/video-craft-playbook/scripts/playbook.py check
python3 ~/.agents/skills/video-craft-playbook/scripts/playbook.py close <slug>
```

`close` 要求案例卡的“蒸馏去向”一节已填写（写了改哪些文件；蒸馏时发现候选其实都不算数，就写“无新知识：<原因>”），且 `check` 通过；随后把卡片移到 `cases/archive/`，台账状态改为“已蒸馏”。

### 4. 例外

- 时间不够：卡片留在 inbox，交付说明写“Playbook 回写：案例卡已建，待蒸馏”。下次 `status` 会提醒。
- 多个 Agent runtime 共用这份手册时，只保留一份源文件，其余以软链或安装指向它；不要分别改副本。

## 倾向性措辞校验

`check` 会在 `references/` 下（本文件除外）拦截表达工具排序的措辞，例如“默认选 / 默认用 / 默认走”“首选”“推荐”“优先用 / 优先选 / 优先考虑”“最佳工具 / 最佳方案”“一律用”。确实要引用原话时，在该行末尾加 `<!-- neutral-ok -->` 并说明是引用。
